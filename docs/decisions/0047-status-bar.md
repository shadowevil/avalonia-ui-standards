# 0047 — Status bar

- **Status:** Agreed, 2026-11-14. Multi-row amendment agreed 2026-11-14.
- **Decision:**
  - `StatusBar` is a Module ([0004](0004-tier-names.md)) for `StandardsWindow.StatusBar`, the window's bottom row ([0022](0022-window-layout.md)). It runs across the whole window, under the sidebar too, on the window background, with no line above it. The slot still takes any content; a `StatusBar` keeps its own side padding.
    - **Why:** Status bars on macOS (a window's bottom bar), Windows (File Explorer, Notepad) and in pro apps (VS Code, Photoshop) are part of the window chrome, not a card inside it; the glass panel stays the only panel ([0015](0015-glass.md)).
  - Height 24 at every density, side padding `SpacingL` (16).
    - **Why:** The references are 22 to 28 px tall (the macOS small bottom bar and Finder about 22, VS Code 22, File Explorer and Notepad about 24 to 28); 24 is the slimmest row on the 4 px grid that holds a 20 px fill with room around it.
  - Zones Leading, Center and Trailing (attached `StatusBar.Zone`, a `StatusZone`), placed as in the toolbar band ([0043](0043-toolbar-band.md)): leading items from the padding, trailing items ending at it, the centre zone centred and moved aside only as far as the others need. Progress goes in the centre zone. No separator lines: text items are `SpacingL` (16) apart and clickable items `SpacingXS` (4) apart (fill to fill); a text item and a clickable one are 8 apart, so their texts are 16 apart.
    - **Why:** VS Code and File Explorer separate items with space, not lines; the gaps keep every text 16 px from the next, whichever kind it is.
  - `StatusBar.Message` (string) is the leading text: a polite live region (`AutomationProperties.LiveSetting` `Polite`), announced when it changes without interrupting.
    - **Why:** Status changes are announced politely on every platform (UIA `LiveSetting`, ARIA `role="status"`); Avalonia 12.1.6 raises the live region change on macOS and Windows.
  - Item kinds:
    - text: a TextBlock, in Caption size ([0012](0012-type.md)) and secondary text (`BaseMedium`, AA on the wash, [0011](0011-colour.md)); not focusable;
    - clickable: a subtle Button or DropDownButton ([0018](0018-button.md), [0021](0021-button-siblings.md)) with the hover fill, its text 8 px into the fill (the 1 px border and 7 px padding), so text lines up at 16 px from the bar's edge as plain text does; a drop-down's chevron is `SpacingXS` after the text and 8 px from the fill's end. The fill is 20 px tall, centred in the bar, with the control radius ([0014](0014-shape.md)); the hit target spans the bar's full 24 px. The focus ring ([0019](0019-focus-ring.md)) follows the fill. The text stays secondary on hover; disabled items keep the disabled text colour;
    - icon with text: an `Icon` ([0026](0026-icon.md)) at 16 px at every density, `SpacingXS` before the text, alone or inside a clickable item;
    - progress: `StatusProgress`, a ProgressBar (160 px) or ProgressRing (16 px) ([0031](0031-slider-and-progress.md)) chosen by `Kind` (`StatusProgressKind.Bar` or `Ring`), with `Value` (0 to 100), `IsIndeterminate`, its `Text` `SpacingS` after it, and an optional cancel button (`IsCancelable`, raising `CancelRequested`): a subtle 20 px icon button with `Icons.X`, `SpacingXS` after the text, named, and its tooltip set, by the `StatusBarCancelText` resource (default "Cancel").
    Any other control can be hosted too.
    - **Why:** VS Code and Photoshop make readouts clickable where they open a setting (a zoom or colour mode picker); the inset fill never touches the window's edge or bottom corners, while the full-height target stays easy to hit.
  - Overflow: the bar never wraps and has no overflow menu. When the items do not fit, first every item takes its shorter texts (attached `StatusBar.ShortTexts`, longest first), then items hide; both in order of attached `StatusBar.Priority` (int, default 0), highest first, ties from the trailing end. When an item hides, the shortened items still shown regain length in the room it left, the last shortened first, a step at a time while the bar still fits. The message never hides; it is trimmed with an ellipsis once nothing else can go. An item's text is a TextBlock's text, a string content, or the first TextBlock in its content or in a panel there; the bar shows a shorter form as the text's current value, keeping the app's bindings, and shows the app's own text again when there is room. A text the app sets while a shorter form shows becomes the item's full text: the form at the same level of its current shorter texts shows at once, so the full text never shows in the short slot, and the bar measures again.
    - **Why:** Status bars drop or cut items when narrow (VS Code by priority, Win32 parts by truncation) rather than hiding them behind a menu; a shorter text keeps an item's information before the item goes.
  - Keyboard: clickable items are ordinary Tab stops in visual order: the rows from the top, then the main row, each leading, centre, trailing. They come after the rest of the window, because the status bar comes last in the window's tree. Text items take no focus. Hidden items and hidden rows take no focus.
    - **Why:** Every action is reachable with Tab; status text is read by assistive technology, not visited.
  - Rows: a `StatusBar` can stack more rows above its main row. The bar's own `Items` and `Message` are the main row, the bottom 24 px; `StatusBar.Rows` is a collection of `StatusBarRow`, each with `Items` that take the attached `Zone`, `Priority` and `ShortTexts`, shown above the main row in collection order, top to bottom. A row has no message. Each row is 24 high with nothing between rows and no divider; its items, gaps, clickable fills and side padding are the main row's. The app shows or hides a row with `StatusBarRow.IsVisible`; the library adds no menu. Each row fits on its own: it shortens, then hides, its own items by priority, and the rows never affect each other. The window's status slot grows with the bar (auto height, at least 24), and a `StatusBar` with rows keeps the module padding rule. Only the bottom row meets the window's bottom corners, so its fills stay at least 8 px from the side edge and 2 px above the bottom, clear of the 16 px corner; rows above keep the same side insets.
    - **Why:** Desktop apps stack secondary readouts above the main row without lines between them (Finder's path bar over its status bar, JetBrains' navigation bar over its status bar), the main row at the bottom as the stable one; keeping the main row's API unchanged leaves existing bars as they are; one live region and one status element avoid announcing the same change twice or listing several bars to assistive technology; rows share the 24 px grid, so nothing needs a new height or spacing.
  - Automation: the bar reports the status bar control type (`AutomationControlType.StatusBar`) and the name of the `StatusBarText` resource (default "Status") unless the app sets one.
  - Light, dark and density follow the Blocks; no motion beyond the Blocks' own.
  - Web ([0045](0045-web-library.md)): `<ui-status-bar>` is a labelled `role="group"` ("Status"), since ARIA has no status bar role and `role="status"` on the whole bar would announce every readout; only the message is a polite live region. `<ui-status-progress>` wraps a `<progress>`, and the Tab order follows the markup.
- **Why:** One slim row for status text, progress and small indicators, as each OS and pro apps show them, built from the library's Blocks, keeping every item's information as long as there is room.
