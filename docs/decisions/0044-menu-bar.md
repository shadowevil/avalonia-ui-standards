# 0044 — Menu bar

- **Status:** Agreed, 2026-11-14
- **Decision:**
  - Apps define their menus once, as Avalonia's `NativeMenu` on the window (`NativeMenu.Menu`), and the application menu (for example About) as a `NativeMenu` on the `Application`. In the macOS layout they go to the macOS system menu bar, as Avalonia exports them. In the Windows layout (Windows and Linux, and any OS set to it with `LayoutMode`, [0022](0022-window-layout.md)) `StandardsWindow` shows the window's menu in an in-window menu row.
    - **Why:** Each OS gets the placement its users expect, from one definition.
  - The menu row is a row of its own directly below the title band and above the toolbar band ([0043](0043-toolbar-band.md)), as in Windows 11 Notepad. It exists only when the window has a menu and the resolved layout is Windows; in the macOS layout it is absent and nothing below it moves.
    - **Why:** The menus get their own place: in the title band they would take the drag area and crowd the title, and narrow windows would clip them; in the toolbar band they would compete with the band's commands for room, and an app with a menu but no toolbar would get a band on Windows only.
  - Height 32 at Normal density and 24 at Compact: the menu titles' own height (Button's density height, [0018](0018-button.md)), so the row adds no padding; the title band above and the toolbar band below give their 8 px. Left inset `SpacingL` (16), so the first title lines up with the sidebar button above and the toolbar band's first item below. The row sits on the window background, with no line under it.
    - **Why:** A smaller row inset in a larger one (24 in 28) leaves 2 px, off the 4 px grid ([0013](0013-spacing-and-density.md)). Renders showed the row reads as its own row without a line.
  - The titles use the Menu bar look of [0036](0036-menus-and-flyouts.md): subtle button titles, glass menus opening 4 px below with their text in line with the title.
  - Dragging: the row's empty area (right of the titles) drags the window, and double-clicking it maximises or restores, as the title band does. Through [0022](0022-window-layout.md)'s chrome roles the row is a title bar and each title (and "…") an interactive element, so pressing a title never drags. This is a deliberate exception to [0043](0043-toolbar-band.md)'s reason for not dragging the toolbar band on Windows.
    - **Why:** The row is part of the window frame, not a row of commands; its empty area sits between the title band and the toolbar band and adds to the area the window is moved by.
  - Narrow windows: titles that do not fit fold, from the end, into a "…" title right after the last title shown, with the toolbar band's three-dots icon (`Icons.DotsThree`), a subtle square title, and the tooltip and automation name "More". It holds the folded titles as submenus, with their items. The four titles of an ordinary app (File, Edit, View, Help) fit at the minimum window width. Which titles show is applied after layout (posted), as in the toolbar band; a folded title keeps the width it had when shown.
    - **Why:** Every menu stays reachable at any width, in the same "…" pattern as the toolbar band. Placing "…" right after the titles keeps it where the folded titles were.
  - Application menu merge: the row appends the Application's menu items after a separator at the end of the Help menu (the last title whose header, without its access key mark and case, matches the `MenuRowHelpHeader` resource, default `_Help`). Choosing one clicks the Application's item. Without a Help menu, the row adds a Help title at the end with the `MenuRowHelpHeader` header to hold them (no separator).
    - **Why:** On macOS these items are in the application menu; on Windows and Linux there is none, and Help is where Windows apps keep About. The header comes from a resource so a translated app finds and names its own Help menu.
  - The row is built by the library from the `NativeMenu`, not by Avalonia's `NativeMenuBar`: a Menu whose items follow the native items. Supported: items, separators, submenus, checkable items (check box and radio), the gesture shown, icons (bitmaps), tooltips, `IsEnabled`, `IsVisible`, header changes, and items and submenus added or removed while the app runs (an open menu stays open when its items change). A click is forwarded to the native item, which raises its `Click` and runs its `Command`. The native item keeps the check state: the app checks or unchecks it in its `Click`, as with a system menu, and the row shows its state.
    - **Why:** In Avalonia 12.1.6 `NativeMenuBar` hides itself whenever the platform exports the menu (macOS, Linux desktops with a global menu bar), so the Windows layout would show no menu there, and it does not act on the items' gestures.
  - Keyboard: Alt alone selects the first title and Alt with an access key opens its menu (Avalonia's access keys; headers mark them with `_`). F10 selects the first title, or closes the menu bar when it is open (added by `StandardsWindow`; Avalonia has no F10). The items' gestures are window shortcuts while the row shows and the platform does not export the menu (an exported menu's system menu bar handles them); a shortcut does nothing while its item or one of its menus is disabled or hidden.
    - **Why:** Windows menu bars open with Alt, access keys and F10; Avalonia's in-window menus do not act on gestures, so shortcuts shown in a menu would not work without this.
  - In the Windows layout on macOS the system menu bar stays as it is, and the row shows as well.
    - **Why:** macOS always shows a menu bar for the active app, so it cannot be emptied, and its command shortcuts keep working.
- **Why:** One menu definition that each OS shows the way its users expect, in the library's menu look, reachable by pointer and keyboard at any window width.
