# 0022 — Window layout

- **Status:** Agreed, 2026-11-12. Inspector and bottom panel slots added 2026-11-16 ([0051](0051-split-panes.md)). macOS native behaviour revised 2026-11-13: `BorderOnly` instead of a borderless window with `hasShadow`, because a borderless window gets only a tight shadow and `BeginResizeDrag` does nothing on macOS, so a borderless window cannot be resized.
- **Decision:**
  - Window frame:
    - The library draws its own window frame: a transparent window shaped as a squircle (radius 16, `CornerRadiusOverlay`; [0014](0014-shape.md)), except on Windows, with a soft shadow and a 1 px border. The window is borderless except on Windows and macOS; the shadow differs per OS (see Native behaviour per OS).
    - Window buttons are drawn by the library, styled per OS: traffic lights on the left on macOS, caption buttons on the right on Windows and Linux.
    - Drag, resize, minimise, maximise and close are handled natively where each OS allows it (see Native behaviour per OS).
    - Opening size (amended 2026-11-14, every OS and frame): a normal window never opens larger than the screen's working area. A side larger than the working area opens as the working area's size, and the window stays centred. A side that fits stays as asked, and the window's `MinWidth` and `MinHeight` still hold. The native macOS frame keeps its own rule, with an inset (see Native behaviour per OS).
      - **Why:** A window larger than the screen leaves its edges, buttons and resize grips out of reach. The drawn frame has no case that needs an inset: a window as large as the working area is simply that large, so it takes the working area and gives the user all the room it asked for.
  - Native behaviour per OS (macOS done in M3 step 6; Windows and Linux in a later step):
    - macOS (done): a titled, resizable, non-opaque window with its title bar and system buttons hidden (`WindowDecorations.BorderOnly`), used when running in a native macOS window (headless renders keep the drawn frame).
      - The system window shadow, the same as other apps' titled windows, derived from the content's alpha, so it follows the squircle. No drawn shadow and no margin: the window is exactly the visible frame, so tiling and positions use it.
      - The system's window corner mask (smaller than the 16 px squircle) does not clip the squircle, and the system adds no hairline of its own; the 1 px border stays the library's.
      - Native resizing from the edges and corners, with the system cursors; the library's resize grips are hidden.
      - Dragging the title band calls Avalonia's move drag, the same native window drag the `TitleBar` role starts. Double-clicking it follows the system setting "Double-click a window's title bar to" (`AppleActionOnDoubleClick`): minimise, do nothing, or otherwise maximise and restore.
      - The client area is not extended (`ExtendClientAreaToDecorationsHint` stays false), so the chrome roles are tagged but not acted on.
      - When maximised, the system keeps its shadow and rounds the window's corners with its own mask.
      - A normal window that would open as wide or as tall as the screen's working area, or more, opens that side `SpacingL` (16) short of the working area at each edge, but never below the window's `MinWidth` or `MinHeight`: a minimum as large as the working area still opens the window there, with the issue below.
        - **Why:** Avalonia.Native 12.1.6 counts a native window as maximised whenever its frame equals the screen's visible frame. macOS squeezes a window that opens larger than the working area to exactly that frame, so the window started out maximised natively while reading Normal, with no frame to restore to, and maximise and restore then acted backwards.
      - The library's traffic lights and Cmd+W and Cmd+M stay.
      - Why not a borderless window with `hasShadow`: macOS gives a borderless window only a small, tight shadow, unlike other windows, and no native resizing. Avalonia 12.1.6 has no resize drag on macOS (`BeginResizeDrag` does nothing there), so only a resizable window can be resized.
      - Why the client area is not extended: in Avalonia 12.1.6 on macOS the only role acted on is `TitleBar`, which starts the same native drag the library already starts, but its double-click always maximises, ignoring the system setting. The resize and button roles do nothing on macOS.
    - Windows: a native resizable border with the system shadow, and no margin. Snap and snap layouts work natively (the maximise button is tagged as the maximise button). Window corners follow Windows 11 (8 px rounded, not the squircle), on Windows only. The content panel and controls keep their squircles.
    - Linux: the drawn shadow and margin stay. The window's input shape is set to the frame (X shape extension), so the margin is click-through, and `_GTK_FRAME_EXTENTS` tells the window manager the margin, so snapping, tiling and positions use the visible frame. The opaque fallback stays for no compositor.
    - All OSes: the title band, resize grips and window buttons are tagged with Avalonia's chrome roles (`WindowDecorationProperties.ElementRole`), so each OS can handle move, resize and buttons natively where the client area is extended. The menu row ([0044](0044-menu-bar.md)) is tagged as title bar and its menu titles as interactive elements, as the sidebar button is.
  - Layout mode: `LayoutMode` (`WindowLayoutMode`: `Automatic`, the default; `MacOS`; `Windows`) sets which OS's layout the window shows. `Automatic` resolves to `MacOS` on macOS and to `Windows` elsewhere, Linux included. The resolved layout sets the window buttons while `WindowButtonStyle` is `Auto` (traffic lights for `MacOS`, caption buttons for `Windows`), whether the toolbar band's empty area drags the window ([0043](0043-toolbar-band.md)), what a title band double-click does (the macOS system setting in the `MacOS` layout on macOS, otherwise maximise or restore), and whether the window's menu shows in the in-window menu row ([0044](0044-menu-bar.md)). The menu's shortcuts work in either layout ([0044](0044-menu-bar.md), Keyboard). It does not change the native frame (macOS keeps its native window, Windows its 8 px corners) or the keyboard shortcuts, which follow the OS the app runs on. It can be switched while the window is open. `ResolvedLayoutMode` (public, read-only, never `Automatic`) is the layout in use and raises a property change when `LayoutMode` changes it, so apps can bind to it or observe it.
    - **Why:** Each OS gets its own layout by default, and the other OS's layout can be seen and checked on any machine (for example the Windows layout while developing on a Mac). The frame and shortcuts belong to the OS and the keyboard in front of the user.
  - Adoption:
    - App windows subclass `StandardsWindow` and fill `Title`, `Toolbar`, `ToolbarBand` (the band below the title band, [0043](0043-toolbar-band.md)), `Sidebar`, `Content` (shown in the glass panel), `Inspector` and `BottomPanel` (the glass panels beside and under it, [0051](0051-split-panes.md)) and `StatusBar` (the `StatusBar` Module, [0047](0047-status-bar.md), or any content).
    - `Backdrop` is a public content slot, drawn between the frame's wash and the window content (behind the title band, sidebar, status bar and glass panel). It is empty by default, and glass blurs and refracts it. Continuous animation in it runs at 30 fps unless `HighRefreshRate` is set ([0016](0016-motion.md)).
    - `ContentPanelBounds` is read-only: the glass panel's rectangle in the `Backdrop` slot's coordinates, updated on layout changes, so backdrops can treat the area behind the panel differently.
    - `BackdropVisibleRegion` is read-only, with a property change only when it changes: the frame's interior less the opaque regions drawn above the backdrop (content marked with `OpaqueRegion.IsOpaque`, and solid glass with an opaque tint, such as the content panel under `GlassQuality` `Solid`), each shrunk by the glass read reach, as a `BackdropRegion` in the `Backdrop` slot's coordinates ([0015](0015-glass.md)). Opaque content inside the `Backdrop` slot is part of the backdrop and does not count. The `Backdrop` slot is clipped to it (no clip while it is the whole interior), and an animated backdrop can read it to skip work that cannot be seen.
      - Why: an opaque document over most of the window hides most of the backdrop; drawing and blurring under it was most of glass's cost there ([0015](0015-glass.md)).
      - Accepted consequence: the clip does not shrink the region Avalonia redraws, so a backdrop that redraws as a whole still redraws the window above it, opaque content included.
    - The frame takes the shared backdrop sample right after the `Backdrop` slot; the content panel, the inspector and bottom panel ([0051](0051-split-panes.md)) and first-level glass in the window's layers read it, the full screen reveal sheet does not ([0015](0015-glass.md)).
    - `IsContentScrollable` (default true): the glass panel scrolls its content vertically, with the 12 px padding inside the scrolled content and the scrollbar and shadows at the panel edge. Accepted consequence: content that scrolls itself (a ListBox, a data grid) gets unlimited height and stops virtualising, so apps set `IsContentScrollable="False"` for such content.
    - `WindowButtonStyle` is `Auto`, `TrafficLights` or `CaptionButtons`; `Auto` follows the layout mode.
    - The window buttons (`WindowButtons`, `TrafficLightButton`, `CaptionButton`) are public Blocks, so other layouts can use them.
  - Values:
    - Title band 48 high (40 Compact), with the title in Body strong ([0012](0012-type.md)).
    - Status bar 24 high at every density, with 16 px side padding (amended 2026-11-14 from 32, 24 Compact, by [0047](0047-status-bar.md)); a `StatusBar`'s rows grow it, 24 per row. The library centres any status bar content vertically in the band, not only single text. It runs across the window under the sidebar and comes last in Tab order. The `StatusBar` Module is in [0047](0047-status-bar.md).
    - Sidebar 8 px from the left.
    - Glass panel 8 px from the sides and bottom, with 12 px padding inside; with the inspector or bottom panel ([0051](0051-split-panes.md)) the content area as a whole keeps these gaps, with 8 px between panels.
    - Frame radius 16 with a 1 px border in Fluent's border colour.
    - Drawn shadow (Linux only): blur sigma 8, offset 8 down, black at 25% (light) or 50% (dark).
    - Resize grips 8 px on the edges and 12 px at the corners; the window buttons take precedence over grips.
    - Shadow and margin differ per OS: see Native behaviour.
    - Minimum size 480×320, applied to the frame (on Linux the window adds the shadow margin).
    - When maximised: square corners, no shadow, no grips (on macOS the system keeps its shadow and corner mask: see Native behaviour). Full screen (macOS only) is in [0049](0049-full-screen.md).
    - Without OS transparency the frame fills the window square, with no shadow.
  - Window buttons:
    - Traffic lights: 12 px dots 8 px apart, 16 px from the left. Close `#FF5F57`, minimise `#FEBC2E`, zoom `#28C840`. Glyphs show on group hover. They are grey with no glyphs when the window is inactive.
    - Caption buttons: 46 × 32, Windows 11's caption button size (Compact 40 × 28, on the 4 px grid), aligned to the top of the title band and flush right. The band height and the content panel's margin do not change. Why: the buttons stay inside the title band so their hover fill never reaches the content panel; Windows 11 draws 46 × 32 caption buttons at the top of the title bar. The glyph (10 px) stays centred in the smaller box. Close hover uses `DangerFill*` with `DangerForeground` ([0011](0011-colour.md)). Glyphs dim when the window is inactive.
    - The buttons follow what the window can do (`CanMinimize`, `CanMaximize`, `CanResize`): see [0049](0049-full-screen.md), which also has the green light's full screen on macOS.
    - Window buttons are not Tab stops (as in native windows); the standard OS shortcuts apply instead: macOS Cmd+W closes, Cmd+M minimises and Ctrl+Cmd+F toggles full screen ([0049](0049-full-screen.md)); Windows and Linux Alt+F4 closes. There is no maximise or restore shortcut: macOS has no standard one for zoom, and Win+Up/Down or Super+arrows are handled by the OS shell.
    - When the window is inactive, the traffic lights use the neutral grey `SystemBaseLowColor` and the caption glyphs use the disabled text colour; hover restores the active look. `WindowButtons` has a public `IsActive` property, set by `StandardsWindow`.
  - Tiers ([0004](0004-tier-names.md)):
    - Window buttons (traffic lights, caption buttons) are Blocks.
    - `StandardsWindow` is the shell Module. It holds the frame (which draws the window background, including the backdrop wash below), the title band, the glass content panel, the status bar, a sidebar slot, and the inspector and bottom panel slots ([0051](0051-split-panes.md)). Its parts are internal, so the layout can evolve.
    - The `Sidebar` Module ([0034](0034-sidebar.md)) plugs into the sidebar slot; with it, the title band shows its button before the title.
    - The app shell Screen (M5) is `StandardsWindow` with the sidebar Module plugged into the slot and the standard content arrangements (sidebar + content, and + inspector), with the collapse stages. Which further Screens follow is an open question ([roadmap](../plan/roadmap.md)).
  - Title band: the title and the toolbar share one band at the top (a unified toolbar).
    - Title icon: in the `Windows` layout, `Window.Icon`, when set, shows at 16 px left of the title text, after the sidebar button if there is one, vertically centred with the title (`SpacingL` from the left edge without a sidebar button, `SpacingM` beside traffic lights, `SpacingS` before the title). Nothing in the `MacOS` layout or without an icon. It follows a live `LayoutMode` or `Icon` change. It is decorative: not hit-testable (a press on it is a press on the title band, so it drags), not a Tab stop, no chrome role, and hidden from assistive technology. Headless window icons save as no image data, so the public, test-only `TitleIconDecoderForTests` lets headless tests, the library's and apps', supply the decoded icon ([0017](0017-app-usage.md)).
  - Areas on the window background: the title band, the menu row below it in the Windows layout of a window with a menu ([0044](0044-menu-bar.md)), an optional toolbar band below that ([0043](0043-toolbar-band.md)), an optional sidebar on the left (a plain list, not a panel) and an optional status bar at the bottom.
  - Content panel:
    - The content sits in one inset glass panel (`GlassBorder`, radius 16; [0015](0015-glass.md)), the only element with the panel look besides the inspector and bottom panel ([0051](0051-split-panes.md)). Where cards may be glass is in [0015](0015-glass.md).
    - It fills the remaining space with `SpacingS` and `SpacingM` gaps ([0013](0013-spacing-and-density.md)), and shrinks to fit beside the sidebar.
    - Layouts: sidebar + content, and sidebar + content + inspector, with an optional bottom panel under the content panel only (layout A: the inspector stays full height); sizes, handles and toggles in [0051](0051-split-panes.md).
  - Backdrop wash (keys `BackdropWash`, `BackdropWashStartColor`, `BackdropWashEndColor`): the window background carries a gentle wash across the whole window, with no visible lines or shapes, so the glass panel reads as glass and text outside it stays calm. It runs from the page colour with the accent mixed in at the top-left (10% light, 14% dark) to the page colour at the bottom-right, and is recomputed for app accents.
    - Web ([0045](0045-web-library.md)): `--ui-backdrop-wash` runs corner to corner over the viewport at `calc(90deg + atan2(100vh, 100vw))`, so its colour lines cross the diagonal at right angles as on desktop.
  - Contrast: text on the backdrop wash and inside the glass panel meets WCAG AA. The backgrounds that the AA text colours ([0011](0011-colour.md)) are checked against include both the wash's extreme colours and the glass panel's tint laid over those extremes. Both are proven by tests. The guarantee covers the library's own wash and glass. Apps that fill the `Backdrop` slot must keep text over it at AA themselves (as [0020](0020-catalog-app.md) does for the catalog's ribbons).
  - Narrow windows collapse in stages: the inspector hides first (below a window width of 1248 it leaves the layout and opens as an overlay at the right edge, [0051](0051-split-panes.md)), then the sidebar collapses to icons, then to a button that opens it as an overlay. The minimum window size is in Values; the sidebar's widths, thresholds and button are in [0034](0034-sidebar.md).
  - Web ([0045](0045-web-library.md)): the shell (classes on the landmarks of [0048](0048-web-html-standards.md)) fills the viewport: no frame, border, shadow or window buttons, since the browser owns the window. The title band, toolbar band slot, sidebar slot, glass panel and status bar keep the desktop sizes. There is no inspector slot until its sizes are decided. The sidebar stages are container queries at fixed widths (container queries cannot read custom properties), mirrored to `data-sidebar-stage` on the shell.
- **Accepted consequence:** Windows and Linux behaviour is verified only on those machines, not from macOS.
- **Why:** One recognisable window on every OS, with the squircle (except on Windows, see Native behaviour) and glass carried through to the window itself, and a clear focus on the content.
